## 2. Field Landscape

Surveyed eight directions: (i) abstraction hierarchies / separation of concerns (Dijkstra 1974, Parnas, Kruchten 4+1); (ii) YAGNI/KISS/"simplest thing that works" (XP, Kelly Johnson 1960); (iii) right-sizing design vs over-engineering; (iv) refactoring and evolutionary design (Fowler, Cunningham tech-debt metaphor 1992, Lehman's law 1980); (v) architecture/design/implementation layering; (vi) requirements/specification completeness and over-specification costs (Boehm cost-of-change curve, missed-requirements rework studies); (vii) design-by-contract and interface specification (Meyer/Eiffel, Hoare triples); (viii) style guides / encoding style choices (review-culture literature); (ix) belief revision — double-loop learning (Argyris 1970s) as the organizational analogue of "refactoring fundamental beliefs."

## 3. Top Findings

1. **Separate concerns along one axis at a time; layering is the mechanism, not the goal.** SoC = divide a complex problem into concerns analyzable in isolation — temporally, by quality, by view, or by size (modularity) — and Dijkstra's 1974 formulation explicitly frames it as ordering one's thoughts, studying correctness one day and efficiency another. CONFIRMED (Dijkstra 1974 via primary quote; Ghezzi, Kruchten 4+1, Laplante concurring). Effect: enables isolated reasoning per concern; no numeric effect size in sources. Source: https://en.wikipedia.org/wiki/Separation_of_concerns
2. **YAGNI is conditional, not absolute: it requires continuous refactoring as a supporting practice.** "Always implement things when you actually need them, never when you just foresee that you need them" (Jeffries); the XP definition states YAGNI used WITHOUT continuous refactoring leads to disorganized code and massive rework (technical debt). CONFIRMED (Jeffries 1998/2001; Succi & Marchesi 2001; Fowler & Beck 1999, all cited). This directly answers T-084: simplify top-down AND refactor constantly are a package deal — either alone fails. Source: https://en.wikipedia.org/wiki/You_aren%27t_gonna_need_it
3. **Refactoring = behavior-preserving restructuring; its payoff is maintainability + extensibility, and skipping it accrues interest-bearing debt.** Cunningham (1992): "Shipping first time code is like going into debt… Every minute spent on not-quite-right code counts as interest"; Lehman's law (1980): complexity of an evolving program increases unless work is done to reduce it. CONFIRMED (Cunningham via debt-metaphor primary quote; Lehman 1980; Kerievsky on continuous refactoring). A missed-requirements study in UAV systems found late rework multipliers (~10X class, doi:10.1017/dsj.2017.13) consistent with the Boehm cost-of-change curve — LIKELY as a Boehm proxy (single study, snippet-level). Sources: https://en.wikipedia.org/wiki/Code_refactoring, https://en.wikipedia.org/wiki/Technical_debt
4. **Specify contracts at interfaces (pre/post/invariant), not implementations.** DbC (Meyer, from 1986; OOSC eds. 1988/1997) prescribes formal, precise, verifiable interface specs — preconditions (client obligation), postconditions (supplier obligation), class invariants — semantically equivalent to Hoare triples, written BEFORE/independently of implementation, and explicitly extended to inheritance and exception handling. CONFIRMED (Meyer coinage + Eiffel trademark record; Hoare-logic roots). This is the "how deep" answer for functional spec: recurse to every component boundary, stop at the boundary. Source: https://en.wikipedia.org/wiki/Design_by_contract
5. **"Refactor your beliefs" has a named, 50-year-old counterpart: double-loop learning.** Single-loop = fix errors within existing rules/goals (thermostat holds 69°F); double-loop = question the 69°F setting itself — revise governing variables, policies, assumptions. Argyris notes organizations actively RESIST it (fear of failure, overemphasis on control). CONFIRMED (Argyris 1970s, thermostat analogy primary quote; Cyert & March 1963 precursor). Implication for the dev protocol: belief-refactor needs an explicit trigger or it will not happen. Source: https://en.wikipedia.org/wiki/Double-loop_learning
6. **Simplicity is a stated design goal with a 60+ year pedigree, but "as simple as possible, but not simpler" is the operative bound.** KISS (Kelly Johnson, U.S. Navy 1960; field-repairable-aircraft origin story) + Einstein paraphrase bound + Saint-Exupéry "perfection when nothing left to take away." LIKELY (well-attested origin; Einstein wording is an editor's paraphrase — flagged as such in source). Answers "no more complicated than required": required = the simplest thing satisfying the contract (cf. finding 4). Source: https://en.wikipedia.org/wiki/KISS_principle

## 4. Design Principles

P1 — **The Ladder Rule (how far down macro→micro to go).** Descend philosophy → architecture → sub-architecture → implementation one concern-axis at a time (finding 1), and STOP descending when the next level down would specify anything already pinned by an interface contract above it. Operational test: if removing a lower-level decision cannot break any contract in finding 4's sense, that level was over-specified — delete it. Each level owns exactly one question: philosophy owns "why/desirability," architecture owns "what/views," implementation owns "how."
P2 — **The Spec-Depth Rule (how deep spec must go, style included).** Specify recursively to every interface boundary with pre/post/invariant triples (finding 4) AND specify style choices exactly once, at the topmost level where a checker can enforce them automatically (linter/formatter/review checklist) — a style rule with no enforcement mechanism is not a spec, it is a wish. T-085's complaint is therefore re-framed: the failure is not "spec didn't go deep enough" but "style was spec'd at a level with no enforcement." Anything neither contract-relevant nor machine-checkable stays out of the spec.
P3 — **The Double-Loop Refactor Rule (when to refactor beliefs).** Single-loop refactor (code smells → micro-refactorings, behavior preserved) runs continuously as hygiene (findings 2–3). Double-loop refactor (question the governing assumption: the architecture, the philosophy, the spec itself) runs on trigger, not on schedule: fire it when (i) the same class of defect recurs after single-loop fixes, (ii) a contract above you changes, or (iii) a simplification at one level forces complication at another (leaky abstraction — the ladder is telling you a belief is wrong). Expect resistance (finding 5) — hence the trigger must be written into the protocol, not left to discipline.

## 5. Not-to-Encode

- **"Always simplify top-down" as an unconditional directive.** Top-down decomposition without the contract-stopping-rule (P1) produces speculative abstraction; YAGNI without refactoring produces debt (finding 2). Encode the pair + the stop test, never the slogan alone.
- **Exhaustive style prescription.** Encoding every stylistic preference as protocol law raises review friction without evidence of defect reduction (style literature surveyed at snippet level only — no CONFIRMED defect-rate effect captured). Encode only machine-enforceable style (P2); keep taste in non-normative examples.
- **Scheduled belief revision ("revisit fundamentals every N weeks").** Double-loop learning is triggered by persistent mismatch, not calendars (finding 5); calendar-triggered philosophy reviews degrade into ritual. Encode the three triggers (P3), not a cadence.
- **Implementation detail inside architecture specs.** Anything at architecture level that names concrete algorithms, file layouts, or copy-pasteable code is a layer violation (finding 1: one axis at a time) — push it down or delete it.
- **Refactoring without a behavior-preservation check.** "Restructure without changing external behavior" is definitional (finding 3); a refactor step with no test/contract pinning the behavior is a rewrite — require the pin.
