## 1. Problem Statement

T-003 observes a scaling failure: as the protocol grows (20 step files, ~5,400 lines, plus README/AGENTS/QUICKSTART/CONSTITUTION/PROTOCOL_MODEL), no single file answers "what is the structure, and is it still true?" Checking means scanning everything, and scanning everything means checking nothing — drift accumulates silently (the fidelity audit that found human-rendering drift is the in-house exhibit). The proposed intervention has two halves: (a) **one authoritative file** that literally is the structure (mastered once, checked instead of the pile), and (b) **copy-then-promote discipline** (change a copy first, rebuild the protocol from the design, overwrite only on pass). The research question: what evidence governs single-master design files, what breaks when copies diverge, and what promotion gates make copy-then-promote safe rather than ceremonial?

## 3. Top Findings (with confidence + effect sizes)

**F1. Master once, reference everywhere — copies must be reads, never second writers. (CONFIRMED, extractor-verified definition)**
The SSoT definition is explicit: every data element is mastered (edited) in only one place; surviving scenarios are (i) never copy, only reference, (ii) copy-for-read with master-only writes (CQRS shape), or (iii) copy-with-write only under a reconciliation mechanism — concurrent-write merging falls back to manual intervention in version control (extracted via sidecar from `https://en.wikipedia.org/wiki/Single_source_of_truth`). Advantages claimed are exactly T-003's motive: fewer mistaken inconsistencies (forgotten duplicate) and simplified version control. T-003 corollary: the design file must declare which scenario it lives in — reference-only or read-copies + master-writes — and any writable copy without a reconciliation rule is by definition not T-003.

**F2. One model, many renderings is the solved form of "one file, many readers." (CONFIRMED, extractor-verified)**
Structurizr's statement is verbatim: write Structurizr DSL once to create "multiple software architecture diagrams from a single model," by the C4 author's reference implementation (extracted via sidecar from `https://structurizr.com/`). The C4 site confirms the mechanism: hierarchical abstractions (system/container/component/code) with hierarchical diagrams plus supporting views, notation- and tooling-independent (extracted via sidecar from `https://c4model.com/`). T-003 corollary: the authoritative file should be the *model* (structure + relations), with QUICKSTART/human renderings *generated or checked* from it — never a second hand-maintained model. T-038's resolved "checker over generator" (c5e573a) is the minimum viable form of this.

**F3. Architecture is the hard-to-change blueprint, "why > how," kept honest by fitness functions. (CONFIRMED, extractor-verified)**
The architecture definition extracted this session: "the set of structures needed to reason about a software system," functioning as "the blueprints for the system," with two laws — everything is a trade-off, and "why is more important than how" — plus the operational sting: architecture "tends to become more complex over time" and architects "should use fitness functions to continuously keep the architecture in check" (extracted via sidecar from `https://en.wikipedia.org/wiki/Software_architecture`). T-003 corollary: the file earns authority only if it records *decisions with reasons* (the why) and ships with at least one fitness function (manifest/Rule-11-style checker), not prose alone.

**F4. Accepted decisions are immutable; change means supersede, never silent edit. (CONFIRMED, extractor-verified process)**
The AWS ADR process: each ADR describes decision + context + consequences; "when the team accepts an ADR, it becomes immutable. If new insights require a different decision, the team proposes a new ADR. When the team accepts the new ADR, it supersedes the previous ADR." Lifecycle is Proposed → (Accepted | Rejected | rework-stays-Proposed), with 10–15-minute read-then-comment review and owner-maintained content (extracted via sidecar from `https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html`). T-003 corollary: copy-then-promote maps cleanly onto ADR states — the copy *is* the Proposed ADR; promotion *is* acceptance with timestamp/stakeholders; post-acceptance edits are forbidden, only supersession.

**F5. Without a master-plus-checker, drift is the default: most repos carry stale references. (CONFIRMED at snippet level; full text UNVERIFIED)**
The Springer study abstract (search-returned, `https://link.springer.com/10.1007/s10664-023-10397-6`): outdated documentation is "pervasive," and across 3,000+ GitHub projects "most projects contain at least one outdated code element reference at some point in their history"; the detector files real issues, some already fixed upstream. Convergent practitioner corroboration: the ArchUnit rule "stop trusting your diagram, start testing it" and the DepCoL Eclipse plugin for "seamless… check consistency during development" (arXiv:1510.08510). T-003 corollary: T-003 without a checker is wishful — the base rate says the pile *will* drift, so promotion must include an automated consistency check (the in-house fidelity-triangle audit is the manual ancestor).

## 4. Design Principles for T-003 (encode these)

**P1. One master, declared scenario: reference-or-read-copy, never two writers.**
Name the file, name its scenario (F1): all other structure-descriptions are references or generated read-copies. Any proposal that hand-edits a derivative instead of the master is rejected at review. Fold owner: P2b LANDSCAPE/spec-architecture plan.

**P2. Copy-then-promote with ADR states: Proposed copy → checked → Accepted-or-Rejected, never silent overwrite.**
The copy is a Proposed ADR (F4): timestamp, owner, stakeholders on promotion; post-acceptance mutation forbidden — only a new superseding copy. Promotion without the check firing green is not promotion, it is drift with ceremony.

**P3. The master holds why, not just what; derivatives hold views, not rival truths.**
Per F2/F3: structure + relations + decision rationale live in the master; QUICKSTART/CONSTITUTION/human renderings are views (generated or checker-verified). The `.omo/plans/spec-architecture.md` goal (justified + self-declaring + non-drifting) is the acceptance test.

**P4. Every promotion runs the fitness function.**
Minimum: manifest check (one row per mechanism, Rule 11) + human-rendering diff against master (checker, per T-038 option B). Aspirational: ArchUnit/DepCoL-style conformance rules and trace-link recovery (S3) as the automated fidelity triangle.

## 5. Not-to-Encode (explicit non-goals)

- **N1. Do not enthrone the file before the checker exists.** A master without a fitness function (F3) rots into S5-base-rate staleness within one sprint; ship master + checker together or ship neither.
- **N2. Do not stuff the master with everything.** The master is structure + decisions + why (F3); provenance logs, session transcripts, and per-run state stay out (they have their own homes: THOUGHT_LOG, transcripts, ledger).
- **N3. Do not allow post-acceptance silent edits.** Immutability-on-accept (F4) is load-bearing; "quick fix directly on master" is the exact failure T-003 exists to prevent.
- **N4. Do not hand-maintain two models.** Any second hand-edited structure-description is a rival master by definition (F1/F2); generate it or check it, never curate it separately.
- **N5. Do not confuse vendor playbook with evidence.** The Atlassian SSoT benefits (S1) are practitioner claims, not measured effects — cite as practice, never as empirical warrant.
